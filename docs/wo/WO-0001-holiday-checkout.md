- **Proposed learned rules:**
  - [price-single-source] Prices, promo rules and cart math live in one pure module imported by both the cart and the payment function; a check script fails if a price or rate literal appears outside it. (source: WO 0001, 2026-11-25)
  - [client-number-is-a-check] A money amount sent by the client (shipping, total) is only compared with the server's own number and answered with 409 plus the server value on mismatch; it is never used to set the charge. (source: WO 0001, 2026-11-25)
  - [qty-bounds] Any quantity from a request is validated as an integer in a stated range before it multiplies a price; negative and fractional values are test cases. (source: WO 0001, 2026-11-25)
  - [quote-then-charge-consistency] When a quote shown to the shopper and the charge are computed by two calls to an external rate service, cache the live quote (same key for both) so a service blip cannot make the charge differ; test "ok on quote, fails on pay" and "down then up" with the cache stubbed. (source: WO 0001 review R1, 2026-11-25)
  - [lock-while-paying] While a payment is being created or confirmed, the cart, promo box and form are frozen (client) and the quote key is re-checked server-side; unfreeze on every exit path including the browser Back button (bfcache `pageshow`). (source: WO 0001 review R1, 2026-11-25)
  - [return-status-all-cases] A payment return page handles every provider status explicitly (succeeded, processing, failed, requires_payment_method, missing/unknown); "no charge was made" is shown only for a failed status. (source: WO 0001 review R1, 2026-11-25)
  - [dest-consistency] A shipping destination is validated server-side as a unit (state in the allowed set, ZIP shape, ZIP region matches the state) before any rate or payment call; the client uses the same functions. (source: WO 0001 review R1, 2026-11-25)
